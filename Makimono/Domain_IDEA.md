# ドメイン設計のアイデア：バレットジャーナルアプリケーション

このドキュメントは、バレットジャーナルアプリケーションの主要なドメインモデル（エンティティと値オブジェクト）に関する議論の要約です。

## 1. エンティティ (Entity) と 値オブジェクト (Value Object) の定義

*   **エンティティ (Entity)**:
    *   **識別子 (ID)** を持ち、その識別子によって一意に区別されます。
    *   ライフサイクルを持ち、時間とともに状態が変化（**可変**）します。
    *   例: `Task`（タスクの内容が変わっても、そのタスク自体は同じものとして識別される）

*   **値オブジェクト (Value Object)**:
    *   識別子を持ちません。
    *   その属性によってのみ区別されます。属性が一つでも変われば、それは別の値オブジェクトとみなされます（**不変**）。
    *   例: `Date`（2025年9月2日という日付は、それ自体がユニークなIDを持つわけではなく、その値によって識別される）

## 2. 主要なドメインモデルの検討

### 2.1. タスク (Task)

*   **`Task`**: **エンティティ**
    *   内容、作成日、完了日、状態などの属性を持つ。
    *   固有のIDを持ち、状態が変化する。
*   **`Task State` (タスクの状態)**: **値オブジェクト**
    *   例: "未完了", "完了", "マイグレーション済み", "キャンセル済み"
    *   タスクの属性として、その状況を記述する不変な値。

### 2.2. デイリーログ (DailyLog)

*   **`DailyLog`**: **エンティティ**
    *   特定の日付に紐づくタスク、イベント、メモ、振り返りを管理する。
    *   固有のID（日付など）を持ち、内容が追加・変更される。
*   **`Reflection Content` (振り返りの内容)**: **値オブジェクト**
    *   振り返りとして記述されたテキストデータそのもの。
    *   不変な値であり、内容が変われば別の値とみなされる。

### 2.3. マイグレーション (Migration)

*   **`Migration`**: 通常、独立した**エンティティではない**。
    *   タスクの状態を変更し、新しいタスクを作成する**「アクション（行為）」**または**「イベント（出来事）」**として捉える。
    *   元のタスクの状態を「マイグレーション済み」に変更し、新しいタスクを生成するプロセス。

### 2.4. その他の主要なログ/コレクション

以下の要素は、それぞれが固有の目的とライフサイクルを持つため、**エンティティ**としてモデル化されます。

*   **`FutureLog` (フューチャーログ)**: **エンティティ**
    *   長期的な計画を管理する。
    *   その中に含まれる個々のエントリ（例: 「来年の夏に旅行を計画する」）は、`FutureLogEntry`のような**エンティティ**としてモデル化されることが多い。
    *   `FutureLogEntry`の**内容（テキスト）**は**値オブジェクト**。

*   **`MonthlyLog` (マンスリーログ)**: **エンティティ**
    *   特定の月の概要やイベントを管理する。
    *   その中に含まれる個々のイベントエントリ（例: 「9月15日 歯医者の予約」）は、`Event`のような**エンティティ**としてモデル化されることが多い。
    *   `Event`の**内容（テキスト）**や**日付**は**値オブジェクト**。

*   **`Collection` (コレクション)**: **エンティティ**
    *   特定のテーマ（例: 読みたい本リスト、プロジェクトXのメモ）に特化した内容を管理する。
    *   その中に含まれる個々のアイテム（例: 「『指輪物語』を読む」）は、`CollectionItem`や`Book`のような**エンティティ**としてモデル化されることが多い。
    *   `CollectionItem`や`Book`の**タイトル**や**著者名**は**値オブジェクト**。

## 3. まとめ

*   **ログやコレクションの「エントリ」や「アイテム」自体は、それぞれが固有の識別子を持ち、ライフサイクルや状態を持つため、エンティティとしてモデル化される傾向があります。**
*   **そして、そのエントリやアイテムの「具体的な情報（テキスト、日付、数値など）」が値オブジェクトになります。**

この区別は、アプリケーションの振る舞いやデータの永続化を設計する上で非常に重要です。
